## Schema Security - PostgreSQL RLS

[Row-Level Security (RLS)](https://www.postgresql.org/docs/current/ddl-rowsecurity.html) lets PostgreSQL filter which rows each database session can read or write. Gencow injects the signed-in user's session into `ctx.db`, so RLS policies declared in your schema apply automatically in procedures and `createCrud()` — no manual `.where(eq(...))` for basic isolation.

For the common case where rows belong to a single user, use `ownerRls()`. It is a preset built on `tableRls()` that matches the row's owner column to the signed-in user from the auth session.

```typescript
import { pgTable, serial, text } from "drizzle-orm/pg-core";
import { ownerRls } from "@gencow/core";
import { user } from "./schema-auth";

export const tasks = pgTable(
  "tasks",
  {
    id: serial("id").primaryKey(),
    title: text("title").notNull(),
    userId: text("user_id")
      .notNull()
      .references(() => user.id, { onDelete: "cascade" }),
  },
  (t) => ownerRls(t.userId),
);

export const categories = pgTable("categories", {
  id: serial("id").primaryKey(),
  name: text("name").notNull(),
});
```

For multi-tenant or org-scoped data, use `tableRls()` directly. It composes PostgreSQL policies from session keys you map in `defineAuth.rls.mapSessionToContext` — for example matching `organizationId` on each row to the active organization in the session, or combining role-based rules with column checks.

```typescript
import { pgTable, serial, text } from "drizzle-orm/pg-core";
import { tableRls, rlsContextKeys } from "@gencow/core";

type AppRls = { userId: string; organizationId: string };
const ctx = rlsContextKeys<AppRls>();

export const projects = pgTable(
  "projects",
  {
    id: serial("id").primaryKey(),
    organizationId: text("organization_id").notNull(),
    name: text("name").notNull(),
  },
  (t) => tableRls(t).matchColumn(t.organizationId, ctx("organizationId")).build(),
);
```

RLS does not lock down a table — it filters which rows inside the table each session can see or change. Without an RLS policy, `ctx.db` queries can return and mutate all rows. Add `ownerRls` or `tableRls` on tables where callers should only touch a subset of rows.

### createCrud()

Prefer `createCrud()` for standard data surfaces because it combines auth, RLS, input validation, and realtime invalidation.

By default, every generated query and mutation requires authorization. Unauthenticated callers receive 401. To opt in to public access, pass `allowAnonymous: true` (this applies `.allowAnonymous()` to each generated procedure). Use only for non-sensitive data.

```typescript
import { createCrud } from "./runtime";
import { tasks } from "./schema";

export const { list, get, create, update, remove } = createCrud(tasks);

export const { list: filteredList } = createCrud(tasks, {
  allowedFilters: ["status", "category"],
});

// Public read/write surface — still subject to PostgreSQL RLS on ctx.db
export const { list: publicList } = createCrud(articles, { allowAnonymous: true });
```

`createCrud()` also accepts an `access` field for operation-level policies. These run at the start of each API call, before any database access. Prefer checks against data already in the user's session (for example `ctx.auth.requireAuth().role`) so the gate stays fast; database lookups are not forbidden, but they add latency on every call.

| Key | Applies to |
|---|---|
| `read` | `list` and `get` |
| `create` | `create` |
| `update` | `update` |
| `remove` | `remove` |

Return `false` (or a promise that resolves to `false`) to reject with Forbidden before the handler touches the database.

```typescript
export const { list, get, create, update, remove } = createCrud(tasks, {
  access: {
    read: () => true,
    create: (ctx) => ctx.auth.requireAuth().role === "admin",
    update: (ctx) => ctx.auth.requireAuth().role === "admin",
    remove: (ctx) => ctx.auth.requireAuth().role === "admin",
  },
});
```

When a caller passes both the auth gate and any `access` policy, row filtering is handled the same way as for hand-written procedures: queries and mutations use `ctx.db`, so PostgreSQL RLS policies on the table still apply to returned and mutated rows.

`createCrud()` requires an `id` primary key such as `serial("id").primaryKey()` or `text("id").primaryKey()`.

## Database Access

```typescript
ctx.db;       // Default. Session-scoped RLS is applied by PostgreSQL.
ctx.unsafeDb; // System-plane handle for audited admin/system work.
```

Use `ctx.db` for normal web app logic. Avoid `ctx.unsafeDb` unless the handler is an audited admin/system path.

Anonymous procedures or anonymous `httpRoute` handlers that use `ctx.unsafeDb`, `rawSql`, `SQL.unsafe`, or `client.unsafe` are blocked by deploy audit unless the preceding comment includes a full exception:

```typescript
// gencow-allow-unsafe-db reason: ... scope: ... owner: ... test: ...
```

## Query Security

With RLS-enabled tables, procedure code does not need to duplicate `.where(eq(tasks.userId, user.id))` for basic owner filtering — PostgreSQL applies your schema policies when `ctx.db` runs the query.

By default, every `procedure.query` and `procedure.mutation` requires an authenticated caller. Unauthenticated requests receive 401 before the handler runs. To expose a public endpoint, add `.allowAnonymous()` to the builder chain.

```typescript
import { procedure } from "./runtime";
import { categories, tasks } from "./schema";

export const list = procedure.query.name("tasks.list").handler(async ({ context: ctx }) => {
  return ctx.db.select().from(tasks);
});

export const publicCategories = procedure.query
  .allowAnonymous()
  .name("categories.list")
  .handler(async ({ context: ctx }) => {
    return ctx.db.select().from(categories);
  });
```

Use `.input()` and `.output()` to validate requests and responses before your handler runs. Any library that implements [Standard Schema v1](https://standardschema.dev/) works — for example Gencow's built-in `v` validator, [Zod](https://zod.dev/), Valibot, or ArkType. Invalid input returns 400; invalid output returns 500.

```typescript
import { z } from "zod";
import { procedure } from "./runtime";
import { tasks } from "./schema";

export const createTask = procedure.mutation
  .name("tasks.create")
  .input(
    z.object({
      title: z.string().min(1).max(200),
      priority: z.number().int().min(1).max(5),
    }),
  )
  .output(z.object({ id: z.number(), title: z.string() }))
  .handler(async ({ context: ctx, input }) => {
    const user = ctx.auth.requireAuth();
    const [row] = await ctx.db
      .insert(tasks)
      .values({ title: input.title, userId: user.id })
      .returning({ id: tasks.id, title: tasks.title });
    return row;
  });
```

Call `ctx.auth.requireAuth()` only when you need the signed-in user inside the handler (for example to stamp `userId` on an insert), not as a separate auth gate at the top of every handler.

## Storage Security

Storage objects are private by default in hosted runtimes. A bare `/api/storage/<id>` URL is anonymous-readable only when the object visibility is `public`.

Use the right API for the file's audience:

| Use case | Pattern |
|---|---|
| Private user attachment preview | `await ctx.storage.createReadGrant(id, { ttlSeconds: 300, disposition: "inline" })` |
| Private user attachment download | `await ctx.storage.createReadGrant(id, { ttlSeconds: 300, disposition: "attachment" })` |
| Public website image/download | `await ctx.storage.store(file, { visibility: "public" })` then `ctx.storage.getPublicUrl(id)` |
| Server-side processing | `await ctx.storage.get(id)` |

Do not store private read grant URLs in long-lived database rows. Read grants expire quickly and are bearer URLs. Store the `storageId`, enforce product authorization through your app tables, and create a fresh read grant inside the query or mutation that returns the file to the browser.

Public visibility means anyone with the URL can read the object. It does not make file listing, upload, delete, or visibility changes public; those remain admin/app-authorized operations.

## Workflow Security

Workflow runtime tables such as `_gencow_workflows`, `_gencow_workflow_steps`, and `_gencow_workflow_events` are platform internals. Do not expose them as public app data.

```typescript
const state = useWorkflow(api.workflows.get, run.id);

export const runs = procedure.query.name("workflowSmoke.runs").handler(async ({ context: ctx }) => {
  const user = ctx.auth.requireAuth();
  // gencow-allow-unsafe-db reason: workflow list scope: owner rows only owner: app-team test: workflow-runs-auth
  return ctx.unsafeDb.execute(sql`
    select * from _gencow_workflows
    where user_id = ${user.id}
    order by started_at desc
    limit 20
  `);
});
```

Rules:

- Workflow list/detail endpoints must be owner-scoped or protected by an opaque token.
- `_gencow_*` tables must stay out of user `schema.ts` and migrations.
- Keep `!_gencow_*` in `drizzle.config.ts` table filters to avoid platform table drift.

## Migration Security Boundary

Gencow Cloud keeps migration responsibilities separate:

- Drizzle Kit generates versioned SQL under `gencow/migrations/`.
- Gencow verifies the authenticated app/database target, immutable bundle, protected platform objects, migration history, and execution outcome.
- Drizzle ORM executes only pending migrations.
- PostgreSQL determines SQL syntax, constraints, locks, transaction rollback, and the resulting database state.

Review and commit generated migrations. Never edit an applied migration, manually change `drizzle.__drizzle_migrations`, or use raw Production SQL to bypass a failed plan. Keep `_system_*` and `_gencow_*` objects out of app schema and migrations.

`gencow db:check [--prod]` performs a generator-free, project-unchanged cloud preflight. Apply that committed source with `gencow db:push [--prod] --existing-bundle`. The check does not execute SQL against a temporary PostgreSQL database, so high-impact migrations still require representative data, lock, and application-behavior testing before Production.

## Cron / Long-Running Work Security

Crawlers, backfills, bulk imports, cleanup jobs, and AI fanout must not be exposed as anonymous public mutations. Use `procedure.internal` for scheduler-only cron actions, or create a separate user mutation with explicit auth and owner-scope checks.

- Put a batch limit on every cron or long-running action.
- Put an AI fanout budget on parallel LLM, embedding, and image calls.
- Avoid unbounded `Promise.all`, recursive loops, unlimited crawling, and thousands of rows loaded in one pass.
- Public mutations that start bulk writes, external API calls, or AI fanout require auth, ownership, rate limits, and credit limits.

## Dangerous Patterns

```typescript
ctx.unsafeDb.update(tasks).set({ done: true }); // can modify other users' rows

const session = ctx.auth.getSession();
ctx.db.insert(tasks).values({ userId: session?.user?.id }); // session may be null

export const crawl = procedure.internal
  .name("crawler.run")
  .handler(async ({ context: ctx }) => runCrawlerWithoutLimits(ctx)); // starts unbounded work
```

Use `ctx.auth.requireAuth()` when null sessions should fail with 401.

## Deploy Audit

`gencow deploy` scans for risky patterns.

| Pattern | Result |
|---|---|
| `ctx.unsafeDb` or raw SQL in protected handlers | Warning |
| Unaudited `ctx.unsafeDb` or raw SQL in public handlers | Deploy block |
| Public exposure of `_system_*` or `_gencow_*` tables | Deploy block |
| Direct client `fetch` calls to procedure RPC | Warning; use hooks instead |

## AI Security

Do not install OpenAI, Anthropic, or other provider SDKs directly in app code. Use only the generated wrapper:

```typescript
import { ai } from "./ai";

const reply = await ai.chat({
  model: "llm/balanced",
  messages,
});

const image = await ai.image.generate({
  model: "gpt-image-2",
  prompt: "A clean app icon",
});
```

`ctx.ai` has been removed. Legacy `/platform/ai/chat` and `/platform/ai/embed` routes are not available. Cloud AI calls must route through OpenAI-compatible platform proxy routes:

- `/platform/ai/v1/chat/completions`
- `/platform/ai/v1/embeddings`
- `/platform/ai/v1/images/generations`

Never put provider API keys into deployed app env vars to bypass the proxy. That breaks credit accounting, spend caps, centralized model allowlists, and secret-zero guarantees.

### Supported models and billing

New hosted chat code should use stable virtual profiles:

- Lowest-cost chat, classification, and extraction: `llm/economy`
- General production chat and agents: `llm/balanced` (Startup/Enterprise)
- Highest quality and complex reasoning: `llm/quality` (Startup/Enterprise)
- Coding and authorized function tools: `llm/code` (Startup/Enterprise)

The platform may replace the concrete model behind a profile without requiring an app code change. Direct chat model IDs are compatibility or model-specific escape hatches, not recommended defaults for new hosted code. Other AI capabilities continue to use their dedicated model IDs:

- Image: `gpt-image-2`, `gpt-image-1.5`, `gpt-image-1-mini`
- Embedding: `text-embedding-3-small`, `text-embedding-3-large`

Deprecated requests are substituted before provider execution:

- `gpt-5.5` -> `gpt-5.4`
- `gpt-4o-mini` -> `gpt-5-mini`

Cloud usage consumes service credits. Local development can use `gencow/.env` `OPENAI_API_KEY` directly and does not consume Gencow service credits. That local direct-provider path must use a concrete OpenAI model ID because OpenAI does not resolve Gencow's `llm/*` names; do not carry the local-only pin into hosted code.

## Search Security

When using `gencow add Search`, keep canonical searchable columns such as `visibility_scope`, `owner_user_id`, and `corpus`.

- Build private scopes with `privateScope(ctx, corpus)` so auth user id is injected server-side.
- Do not copy plan/tier capability gates into app code; use `ctx.search()`, `ctx.vectorSearch()`, and `ctx.hybridSearch()`.
- Keep result ACLs aligned with both scope columns and existing RLS policies.
- Use selective `tuning` overrides only. Do not expose provider or DB internals as app-level knobs.

## Grounded RAG Security

`rag.askGrounded()` and `reranker.answerGrounded()` assemble citations from canonical `rag_*` tables through `ctx.grounding.answer()`.

- `rag.ingest()` documents are not the source for grounded answers. Use `documents.ingest.*` for grounded corpora.
- Canonical embeddings use `/platform/ai/v1/embeddings`; do not recreate legacy `ctx.ai.embedMany()` paths.
- Do not attach full source text to answer payloads.
- Fix `corpus`, `visibility`, and `ownerUserId` scope at the initial request and do not broaden it during retries.
- Snippets should contain only the minimum excerpt required for citation.

## Document Convert / OCR Security

`wf.services.document.convert()` is a workflow-only platform OCR/document conversion path.

- Do not call OCR providers directly from normal procedures.
- Keep OpenAI, Gemini, and custom VLM provider keys in platform configuration only.
- `provider: "auto"` and `mode: "force-ocr"` follow platform admin policy.
- Sending private corpus documents to external providers must be explicitly allowed by platform policy.
- Do not log original document text, provider tokens, or secret headers.
